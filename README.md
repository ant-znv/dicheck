# DI_Check

Локальное веб-приложение для проверки должностных инструкций (ДИ) через LLM API (DeepSeek, z.ai). Проверка выполняется по методике госконтракта (44-ФЗ/223-ФЗ, ТК РФ): приложение анализирует ДИ, формирует отчёт с правками и может исправить документ.

## Возможности

- Работает как настольное приложение: собственное окно (WebView2) — без браузера и без окна консоли; закрытие окна останавливает приложение.
- Загрузка ДИ в форматах `.docx`, `.doc`, `.pdf`, `.txt`, `.md`, `.odt` — по одному файлу или пакетом (до 20 файлов, до 20 МБ каждый).
- Контекст госконтракта: предмет, тип занятости (полная/частичная), дополнительные условия.
- Проверка по системному промту на основе методики госконтракта (44-ФЗ/223-ФЗ, ТК РФ); промт редактируемый, есть вариант по умолчанию.
- Отчёт прямо в UI с итоговой оценкой (ок / риск / несоответствие) и структурированными правками «Было» / «Будет» с обоснованием.
- Экспорт отчёта в Markdown, HTML и DOCX.
- Исправление ДИ: детерминированное применение правок в исходный `.docx` с сохранением форматирования; если правку нельзя применить автоматически — LLM-фолбэк.
- Пакетное «Исправить все» — исправленные документы скачиваются одним zip-архивом.
- История проверок: все проверенные ДИ, их исправленные версии и найденные замечания сохраняются локально; карточка документа пополняется должностью и подразделением (LLM-извлечение в один клик, по одному или пакетом), а все исправленные версии выгружаются одним zip-архивом.
- Пересечения обязанностей: приложение извлекает из каждого проверенного ДИ список конкретных обязанностей и находит (LLM) дублирование фактической работы между сотрудниками РАЗНЫХ подразделений; отчёт о пересечениях сохраняется (последние 5), повторные запуски используют кэш обязанностей и не тратят лишние LLM-вызовы.
- Экспорт исправленных ДИ по своему шаблону: загрузите .docx-шаблон с плейсхолдерами `{{ДОЛЖНОСТЬ}}`, `{{ПОДРАЗДЕЛЕНИЕ}}`, `{{НАЗВАНИЕ}}`, `{{ТЕКСТ}}`, `{{ДАТА}}`, `{{ЗАМЕТКИ}}` — и zip-выгрузка исправленных ДИ соберётся по нему без LLM: метаданные подставятся вместо простых плейсхолдеров (в абзацах и таблицах, с сохранением форматирования), а на место `{{ТЕКСТ}}` вставится содержимое исправленного документа.
- Отмена запущенной проверки, восстановление последней проверки после обновления страницы (F5).
- Выбор провайдера (DeepSeek / z.ai) и модели, проверка соединения.

## Быстрый старт

### Вариант A1: установщик (для конечного пользователя)

1. Запустите `DI_Check_setup.exe` и следуйте мастеру (установка без прав администратора, в `%LOCALAPPDATA%\Programs\DI_Check`).
2. Ярлык появится в меню «Пуск» и (по желанию) на рабочем столе; при установке можно сразу запустить приложение.

Удаление — через «Установка и удаление программ» («DI_Check»). Личные данные (API-ключ, настройки в `%APPDATA%\DI_Check`) при удалении сохраняются.

### Вариант A2: портативная сборка (без установки)

1. Распакуйте `DI_Check_portable.zip` в любую папку.
2. Запустите `DI_Check.exe` — откроется окно приложения (сервер — `http://127.0.0.1:8787`); браузер не нужен.

Python и Node.js на машине не нужны: фронтенд и промт встроены в exe (иконка приложения — `resources/app.ico`, генерируется скриптом `resources/make_icon.py`).

Опции командной строки:
- `--port N` — запуск на другом порту;
- `--console` — режим с консолью и браузером вместо окна приложения (лог в консоль, браузер открывается сам);
- `--no-browser` — не открывать браузер автоматически (действует только вместе с `--console`).

Если порт уже занят (приложение уже запущено), exe просто откроет окно к работающему экземпляру. Для остановки закройте окно приложения.

### Вариант B: из исходников (для разработчика)

Требования: Windows 10+, Python 3.12+, Node.js 20+.

1. Склонируйте репозиторий.
2. Запустите `start.bat` — он создаст виртуальное окружение `.venv`, установит зависимости, при первом запуске соберёт фронтенд, поднимет сервер на `http://127.0.0.1:8787` и откроет браузер.

Для старых файлов `.doc` нужен установленный Microsoft Word (используется Word COM).

## Настройка

В настройках приложения (UI):

- **API-ключ** — введите ключ выбранного провайдера. Ключи хранятся только локально, зашифрованными Windows DPAPI, в `%APPDATA%\DI_Check\config.json`.
- **Провайдер и модель** — DeepSeek или z.ai (GLM); можно проверить соединение и подгрузить список моделей.
- **Системный промт** — редактируемый; кнопка сброса возвращает промт по умолчанию (на основе `analiz-DI-goskontrakt-v4.docx`, раздел «2. Промт для ИИ»).

Приватность: всё работает локально, ключи никогда не покидают машину — они отправляются только в API выбранного провайдера при выполнении проверки. Через API приложения ключи не возвращаются (только флаг наличия ключа). Сервер слушает только `127.0.0.1` (loopback), который Windows Firewall не фильтрует, — запрос разрешений файрвола не появляется.

История проверок также хранится только локально: `%APPDATA%\DI_Check\history.db` (SQLite). Туда автоматически попадают все проверенные ДИ — исходные документы с отчётами и замечаниями, а также исправленные версии; проверка сохраняется в историю даже после перезапуска приложения. База удаляется вместе с удалением данных приложения (`%APPDATA%\DI_Check`).

### Пересечения обязанностей

На странице истории выберите документы (или возьмите все) и запустите поиск пересечений: приложение извлечёт из каждого ДИ список конкретных обязанностей (общие формулы вроде «соблюдает трудовую дисциплину» пропускаются) и одним LLM-вызовом на группу до 8 документов найдёт одну и ту же фактическую работу, закреплённую за разными подразделениями. Связи «подчинённый-руководитель» внутри одного подразделения и пересечения внутри одного отдела не включаются. Извлечённые обязанности кэшируются вместе с документом: повторный поиск по тем же версиям ДИ проходит без повторных LLM-извлечений. Последние 5 отчётов хранятся в БД истории.

### Экспорт исправленных ДИ по шаблону

По умолчанию исправленные ДИ выгружаются как есть. Если нужен фирменный бланк — загрузите шаблон (.docx) в разделе истории: это обычный документ, в тексте которого расставлены плейсхолдеры `{{ДОЛЖНОСТЬ}}`, `{{ПОДРАЗДЕЛЕНИЕ}}`, `{{НАЗВАНИЕ}}`, `{{ДАТА}}`, `{{ЗАМЕТКИ}}` и `{{ТЕКСТ}}` — место, куда вставляется содержимое исправленного документа. Плейсхолдеры работают и в таблицах; форматирование абзаца шаблона сохраняется. Экспорт «по шаблону» собирает zip детерминированно, без обращения к LLM. Шаблон хранится локально (`%APPDATA%\DI_Check\report_template.docx`) и его можно в любой момент удалить (вернётся выгрузка как есть).

## Обновления

Приложение умеет самообновляться через GitHub Releases: при старте приложения проверку последнего релиза делает интерфейс (frontend) — тихо, при загрузке страницы; в настройках (раздел «Обновления») можно проверить и установить новую версию одной кнопкой — установщик скачается во `%TEMP%`, сам закроет приложение, обновит файлы и запустит новую версию (настройки и ключи в `%APPDATA%\DI_Check` сохраняются). Автообновление работает в установленной версии (Inno Setup); для портативной сборки приложение подскажет скачать новый ZIP со страницы релизов и заменить папку вручную.

Репозиторий обновлений уже прописан по умолчанию (`ant-znv/dicheck`); при необходимости он меняется в настройках (раздел «Обновления»), там же для приватного репозитория сохраняется токен GitHub (PAT с правом `Contents: read`).

### Как выпустить новую версию

1. Поднимите версию в `backend/app/version.py` (`APP_VERSION`).
2. Закоммитьте и поставьте тег: `git tag v0.2.0 && git push origin v0.2.0`. Тег пушьте **отдельной командой**: если пушить ветку и несколько тегов одним `git push`, GitHub может не создать прогоны для тегов (тогда досоздайте: `gh workflow run build.yml --ref vX.Y.Z`).
3. GitHub Actions (`.github/workflows/build.yml`) соберёт фронтенд, прогонит тесты, соберёт exe и установщик и опубликует релиз с файлами `DI_Check_setup.exe` и `DI_Check_portable.zip`.
4. Установленные приложения увидят обновление (по тегу релиза) и обновятся в один клик.

## Tesseract OCR (опционально)

Для сканированных PDF можно установить [Tesseract OCR](https://github.com/tesseract-ocr/tesseract) с языковыми пакетами `rus` + `eng`. Без него приложение корректно обработает текстовые PDF, а для сканов покажет подсказку об отсутствии OCR.

## Для разработчиков

### Структура репозитория

- `backend/app/` — FastAPI-бэкенд (порт 8787): `main.py` (endpoints, джобы проверок в памяти), `extractors.py` (извлечение текста из документов), `llm.py` (OpenAI-совместимый async-клиент на httpx), `settings.py` (конфиг в `%APPDATA%\DI_Check\config.json`, ключи шифруются DPAPI), `history.py` (история проверок в `%APPDATA%\DI_Check\history.db`), `default_prompt.md` (промт по умолчанию).
- `frontend/` — React 19 + TypeScript + Vite 7 + Tailwind CSS v4; сборка в `frontend/dist`, раздаётся бэкендом как статика.
- `backend/testdata/` — тестовые ДИ, генераторы (`make_sample.py`, `make_samples_batch.py`) и сквозной тест `verify_batch.py`.
- `backend/tests/` — pytest-сьют бэкенда (LLM мокается, сеть/ключи/Word/Tesseract не нужны).
- `docs/api-contract.md` — контракт API фронтенд↔бэкенд; при изменении API обновлять его.

### Команды

| Действие | Команда |
|---|---|
| Запуск всего | `start.bat` |
| Бэкенд вручную | `.venv/Scripts/python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8787` |
| Тесты бэкенда | `.venv/Scripts/python.exe -X utf8 -m pytest backend/tests -q` |
| Сборка фронтенда | `cd frontend && npm run build` |
| Сборка портативного exe | `build_exe.bat` (запускает PyInstaller по `DI_Check.spec`) |
| Сборка установщика | `build_exe.bat` (шаг Inno Setup; требует ISCC — Inno Setup 6/7) |
| CI/релизы | `.github/workflows/build.yml`: push в main — артефакты, тег `vX.Y.Z` — GitHub Release |

Сборка создаёт `dist\DI_Check\` (DI_Check.exe + `_internal`), zip-архив `DI_Check_portable.zip` и установщик `dist\installer\DI_Check_setup.exe` (если найден Inno Setup). В exe встроены фронтенд и промт. Установщик описан в `DI_Check.iss`: установка без прав администратора, ярлыки в меню «Пуск» и на рабочем столе (опционально), запуск после установки, остановка запущенного приложения и чистка окружения PyInstaller при установке поверх (важно для самообновления). Версия установщика передаётся как `/DMyAppVersion=X.Y.Z` (локально берётся из `backend/app/version.py`).

Сквозной тест с реальным API-ключом (нужен запущенный сервер): `backend/testdata/verify_batch.py` — check → export docx → fix-all.

Примечание: при работе в консоли Windows вывод русского текста из Python — только в файл с `encoding='utf-8'` либо с `python -X utf8` (консоль cp1251 падает на `print`).

## Известные ограничения

- Джобы проверок живут в памяти процесса — после перезапуска сервера недоступны сами джобы (файлы, /fix по ним), но результаты проверок остаются в истории (`%APPDATA%\DI_Check\history.db`). Завершённые джобы хранятся в памяти до 24 ч или пока не наберётся 50 джоб.
- До 20 файлов на проверку и 20 МБ на файл; извлечённый текст длиннее 120 000 символов обрезается.
- Для файлов `.doc` (старый формат) необходим установленный Microsoft Word.
- Для сканированных PDF без установленного Tesseract OCR распознавание недоступно.
- Работает только на Windows (хранение ключей через DPAPI, Word COM, портативная сборка).

### Диагностика

В обычном (оконном) режиме консоли нет: логи пишутся в `%APPDATA%\DI_Check\logs\di_check.log` (ротация 5 МБ, 3 копии), рядом — `di_check.stdout.log` и `di_check.stderr.log` для необработанного вывода. При сбоях приложите эти файлы к описанию проблемы. Для диагностики с живой консолью запустите exe с флагом `--console` — лог пойдёт в консоль, браузер откроется сам.
